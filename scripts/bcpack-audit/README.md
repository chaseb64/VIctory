# Native Windows BCPack verification

This supplemental fork workflow runs the paired guest title on the baseline and candidate using the standard Windows Server 2025 x64 runner. Its artifact contains the tested Git revisions and complete guest TAP logs. The earlier combined workflow also ran workspace tests, both Clippy configurations, asset policy and the entropy replay. [Combined workflow](https://github.com/chaseb64/VIctory/actions/runs/45583602232)

The earlier combined workflow’s entropy replay generates records first, encodes them with Ahmet Dedeler’s public bcpack-rs encoder and checks the contiguous input through its independent decoder. It compares VIctory’s decoded lane records with the original symbols. The upstream release uses MIT OR Apache-2.0, and its rANS implementation credits Microsoft’s MIT-licensed silicon-rans. The workflow compiles those modules from the pinned checkout. VIctory reads its existing shipped tables under its repository asset policy. [bcpack-rs](https://github.com/Ahmet-Dedeler/bcpack-rs/tree/b1c3099a3402de8b76c9263a828791bd8bc0c930) · [Third-party notices](https://github.com/Ahmet-Dedeler/bcpack-rs/blob/b1c3099a3402de8b76c9263a828791bd8bc0c930/THIRD_PARTY_NOTICES.md) · [VIctory asset policy](https://github.com/Marvisak/VIctory/blob/940d32f69b22265690a0b5a15d6ded572ba33baf/docs/asset-policy.md)

The queue check extends 0xkn0wh3r3’s conformance title on both revisions. It adds generated BC1 requests and checks status, output and guard bytes for memory, file and zlib paths. The original harness checks its five known divergences. The paired driver also checks the exact additional baseline failure and the corrected candidate output. [Upstream conformance proposal](https://github.com/Marvisak/VIctory/pull/2057)

AI-assisted using OpenAI Codex. GPT-6.2 Astra (Ultra) handled integration. GPT-6.2 Astra (High) produced and reviewed entropy and fixture evidence. GPT-6.2 Sol (High) contributed the queued fixtures, format checks and measured performance refinement. GPT-6 Luna (Medium) contributed reference and Windows evidence handling.

The supplemental paired run also checks two generated blocks for each of BC1, BC3, BC4, BC5, BC6H and BC7 through a normal memory request and through a zlib-wrapped memory request. Each of the twelve cases checks completion, exact block bytes and both destination guards. BC1 expected bytes come from the bcpack-rs block assembler. BC3/4/5 use independently chosen target block fields and the shipped prediction/rank tables. BC6H/7 use synthetic input records assembled by SixNG’s independently maintained block routines, with public BPTC partition constants. The source literals contain generated test values. No third-party decoder implementation was added. [SixNG algorithms](https://github.com/holdmysocks/SixNG/tree/993370b9f509127b11df93ea3963cd99f75d7950) · [bcdec](https://github.com/iOrange/bcdec/tree/80859ed3b7afb1c527a2a99d70c61457bea72d0c)

A further raw BC1 request splits the two-byte refill for red endpoint deltas −16 and +15. Both baseline status errors are required to be HRESULT 0x8007000d. The integrated revision must deliver the two expected blocks and keep the guards intact.
